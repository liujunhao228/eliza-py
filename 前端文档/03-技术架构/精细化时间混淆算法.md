# 精细化时间混淆算法设计

## 1. 设计目标

将“匹配时长”这一物理特征转化为无意义的噪声，确保用户无法通过等待时间长短推断对手身份。

*   **去特征化**：消除“瞬间匹配=真人”、“长等待=AI”的直觉线索。
*   **分布一致性**：确保匹配到真人与匹配到 AI 的等待时间概率密度函数（PDF）在用户感知层面高度重合。
*   **体验平衡**：在混淆时间的同时，避免过度牺牲用户体验（如无意义的漫长等待）。

## 2. 核心变量定义

*   $T_{entry}$：用户入队时间戳。
*   $T_{match}$：后台撮合成功时间戳。
*   $T_{notify}$：前端收到结果的时间戳。
*   $W_{real}$：真实等待时长，$W_{real} = T_{match} - T_{entry}$。
*   $W_{perceived}$：用户感知等待时长，$W_{perceived} = T_{notify} - T_{entry}$。
*   $T_{min}$：最小阈值（如 2秒），防止瞬间返回暴露信息。
*   $T_{max}$：最大容忍阈值（如 7秒），超过此时间需优先考虑用户体验。

## 3. 分段混淆策略

算法根据 $W_{real}$ 落入的时间区间，采取不同的混淆策略。

### 3.1 阶段一：瞬时匹配区 ($W_{real} < T_{min}$)

**场景**：队列中恰好有人，瞬间撮合成功（通常是真人，或 20% 对照组的 AI）。
**风险**：用户点击后立即反应，会推测“这么快肯定是有人一直在等”。
**策略**：**固定时长填充**。

*   **算法逻辑**：
    设定目标感知时间 $W_{target} \in [T_{min}, T_{target}]$（例如 3s-5s）。
    $$T_{notify} = T_{entry} + \text{Random}(T_{min}, T_{target})$$
*   **效果**：无论后台是 0.1秒撮合成功，还是 1.5秒成功，用户都要等待一个“合理的加载时间”才看到结果。这掩盖了“瞬间撮合”的物理特征。

### 3.2 阶段二：自然等待区 ($T_{min} \le W_{real} < T_{max}$)

**场景**：用户排队了一段时间（如 4秒），后台撮合成功（可能是刚来的真人，或触发超时逻辑）。
**风险**：此区间处于“模糊地带”，如果不加处理，时间分布可能泄露概率信息。
**策略**：**随机抖动**。

*   **算法逻辑**：
    不进行大幅度的延迟填充，而是增加微小的随机抖动，打齐时间尾数。
    $$T_{notify} = T_{match} + \text{Random}(0s, 1s)$$
*   **效果**：保持自然感，同时通过抖动模糊确切的匹配时刻。此区间内，真人与 AI 的等待时间分布已自然混合，无需强制干预。

### 3.3 阶段三：长尾超时区 ($W_{real} \ge T_{max}$)

**场景**：排队很久（如 60秒）未匹配到真人，系统强制分配 AI。
**风险**：用户等待焦虑，且“很久才匹配到”容易联想到“没人所以塞了个AI”。
**策略**：**即时反馈**。

*   **算法逻辑**：
    一旦判定超时或触发 AI 兜底，立即通知，不再增加额外延迟。
    $$T_{notify} = T_{match}$$
*   **理由**：用户耐心已耗尽，体验优先级高于混淆。且从统计上看，真人匹配也可能因为网络波动或对手确认慢而导致长时间等待，此时区分度不明显。

## 4. 核心算法实现逻辑

以下是服务端在“原子结算”完成后，计算通知时间的伪代码逻辑：

```python
import time
import random

def calculate_notify_time(entry_time: float, match_time: float) -> float:
    """
    entry_time: 用户入队时间
    match_time: 后台撮合完成时间
    return: 应当推送给前端的时间戳
    """
    
    # 配置参数
    T_min = 2.0    # 最小感知等待
    T_target = 5.0 # 目标等待上限
    T_max = 7.0    # 自然等待区上限
    
    real_wait = match_time - entry_time
    
    if real_wait < T_min:
        # 阶段一：瞬时匹配 -> 强制填充到 [T_min, T_target] 区间
        # 随机选择一个时长，模拟“寻找对手”的过程
        perceived_wait = random.uniform(T_min, T_target)
        return entry_time + perceived_wait
        
    elif real_wait < T_max:
        # 阶段二：自然等待 -> 增加少量随机抖动 (0~1s)
        # 目的是防止多个用户在同一秒收到结果，增加随机性
        jitter = random.uniform(0, 1.0)
        return match_time + jitter
        
    else:
        # 阶段三：长尾等待 -> 立即返回
        # 用户体验优先
        return match_time

# 示例场景
# 场景A：瞬间匹配到真人 (real_wait=0.2s)
# 结果：notify_time = entry_time + 3.5s (用户感觉等了3.5秒)

# 场景B：等了3秒匹配到AI (real_wait=3.0s)
# 结果：notify_time = match_time + 0.2s (用户感觉等了3.2秒)
```

## 5. 针对“20% 对照组”的对称性处理

在文档提到的 **2.2 原子结算** 中，当触发 20% 概率的对照组逻辑时：
*   发起者 A（刚进队）：$W_{real} \approx 0$。
*   等待者 B（已在队中）：$W_{real} > 0$。

**精细化处理方案**：
双方必须同时收到通知，以维持“我们在同一时刻匹配成功”的错觉。

1.  **计算规则**：
    系统应以 **发起者 A** 的视角为主计算通知时间（因为 A 需要填充延迟）。
    $$T_{notify\_A} = T_{entry\_A} + \text{Random}(T_{min}, T_{target})$$
    
2.  **同步通知**：
    对于等待者 B，虽然 B 已经等了一会儿，但系统强制将 B 的通知时间也对齐到 $T_{notify\_A}$。
    *   若 $T_{notify\_A} < T_{match\_B}$（理论上不可能，因为 A 进队时 B 已经在等）：无此情况。
    *   若 $T_{notify\_A} > T_{match\_B}$：B 的通知被延迟，等待 A 的“填充时间”结束。
    
    *逻辑解释*：这会让 B 觉得“终于匹配到了”，而 A 觉得“花了几秒找到了 B”。双方的时间体验被算法“剪辑”过，但在用户感知上是连贯且合理的。

## 6. 总结：混淆效果对比表

| 场景 | 真实后台耗时 | 用户感知耗时 | 混淆策略 | 用户心理推测 |
| :--- | :--- | :--- | :--- | :--- |
| **瞬时真人** | 0.1s | 3.5s | **时间填充** | "有点慢，可能在排队，可能是真人。" |
| **瞬时AI (对照组)** | 0.1s | 3.5s | **时间填充** | "有点慢，可能在排队，可能是真人。" |
| **中途真人** | 4.2s | 4.5s | **随机抖动** | "正常速度，应该是匹配到了人。" |
| **中途AI (对照组)** | 10.0s | 10.3s | **随机抖动** | "等了一会儿，应该是匹配到了人。" |
| **超时AI** | 60.0s | 60.0s | **立即返回** | "太久没人才给的AI吧？" (无法完全避免，但在容忍范围内) |

通过此算法，**除了极端的长尾超时情况**，绝大多数匹配场景（无论是真人还是 AI）的等待时间都被压缩在 **$[T_{min}, T_{max}]$** 的一个平滑区间内，用户将无法利用“时间线索”来攻破图灵测试的盲测环境。
